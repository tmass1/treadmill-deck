# Treadmill Deck — notes for Claude

C1250 Deck: a console app for the NordicTrack Commercial 1250 that replaces iFit on the treadmill's
own screen. See README.md for the overview and ROADMAP.md for what's next.

**Private things live elsewhere.** The signing key, the site key and the owner's own setup (home
network, Home Assistant entities, accounts, deploy tokens) are in a private repo cloned next to this
one as `../treadmill-deck-private` (Tommy's: tmass1/treadmill-deck-private; read its NOTES.md). Never
put a key, a keystore, an APK, a home address or an account id in this repo; it is public.

## Facts that matter
- Console: **Android 9** iFit Gen 8 tablet (MediaTek, model MalataMediatekArgon2, build MKA2_20230329). Android 9 has no Wireless debugging, and ADB's "Allow USB debugging?" prompt never shows (iFit hides system UI), so `installer/install.sh` often can't authenticate; install by serving the APK from a computer (`python3 -m http.server 8000`) and opening it in the console's Browser.
- **Newer iFit has no separate GlassOS service** (seen after an Oct 2026 factory reset): port 54321 closed, no `com.ifit.glassos_service`. Installed: `com.ifit.arda` 1.0.26 (iFit), `com.ifit.eru` 2.13.9 (updater, system uid), `com.ifit.launcher`, `com.ifit.standalone`. Settings → Treadmill → Diagnostics (`Diagnostics.java`) lists USB devices, tty/hidraw nodes, open local ports, and what each iFit app's dex mentions; **Share iFit apps** serves their APKs on `http://<console>:8765/` while the sheet is open (a thread per connection, the whole request read before replying).
- **The motor board is a USB HID device**, `213c:0002` (ICON, product 2 = **FitPro 1**; one interface, class 3 = HID). `FitPro.java` speaks the protocol, worked out from arda 1.0.26 with jadx (obfuscated, but `compiled from: X.kt` comments name them: `qe/c` UsbConsoleConnection, `jd/b` FitPro1UsbConsoleConnection, `id/*` commands, `fd/a` BitField, `hd/*` converters, `kd/e` FitPro1ConsoleImpl). The whole protocol is in the class comment. **USB permission** comes from `com.ifit.eru`: its exported `GrantUsbPermissionReceiver` grants the board to whatever `packageName` a `com.ifit.eru.USB_PERMISSION_REQUEST` broadcast names. Only one app can claim the board.
- **The app drives the belt over USB** (`Belt.java`, 1.8.0+): it claims the board while on screen (pauses a running belt and lets go in onStop), polls READ_WRITE every 250 ms, and the page's commands only queue writes (mode 2 run / 3 pause / 4 results, then 1 idle after 2.5 s; speed and incline only sent while running, apart from levelling the deck below). **The end of a workout levels the deck** (1.13.1): `Belt` asks for 0% (the board's lowest, if that's above 0) in the same message as the stop, then every tick until the board reads it back at idle, for at most 20 s. It also catches the console's own STOP key (the board leaving run or pause for results or idle). Pausing doesn't level. A pulled safety key cancels it and never starts it, because clipping the key back on isn't asking the deck to move. The GlassOS fallback doesn't level. Not yet proven on the real board: `F_GRADE` was only ever written while running, so whether it keeps moving in results and idle is for the treadmill to show. Setup mirrors iFit's FitPro1ConsoleImpl for a treadmill: REQUIRE_START_REQUESTED (108) = 1, so the console's Start key raises START_REQUESTED (96) instead of starting the belt and the page answers with its countdown; IDLE_MODE_LOCKOUT (95) = 0. If iFit still holds the board, the app calls `killBackgroundProcesses` on it once, then asks for a force-stop. Diagnostics → Motor link reports the startup exchange; Diagnostics → Belt test runs the slowest speed for 10 s and stops. GlassOS (gRPC on `localhost:54321`, mTLS, `client_id: com.ifit.wolf`; certs copied from the iFit packages, never committed) stays as the fallback when no board is attached.
- ACTUAL_KPH/ACTUAL_GRADE (16/17) read 0 during a run on this board, so Belt uses the set speed/incline until an actual field ever reads non-zero. The console's own speed and incline keys change the board's set values; Belt pushes `setKph`/`setIncline`/`pending` and the page adopts them as its targets when none of its own writes is queued or under 1.5 s old. Distance, time and calories are the page's own; each run also stores the board's raw distance and time counters (fields 4 and 11, units unconfirmed) as `board: {distRaw, timeRaw}`.
- **Before the belt moves** (1.13.0): `begin`, `start` (unless resuming) and Belt test all ask `canMove` first: the motor answering with the safety key in (`connState`), and the safety sheet agreed (`safetySheet`, `deck.safety`; bump `SAFETY_V` if its meaning changes). Agreeing never starts the belt: they tap Start again. **Limits:** `takeBoard` adopts the board's own speed and incline limits (`SPEED_MIN` and friends are defaults until then, and in the demo), and `Native` holds every command to them. **Compatibility** (`Belt.java`): `TESTED` lists the models it has been run on. Any other board that answers as a treadmill or incline trainer, has the fields it writes and reports its limits is `untested`: the sheet warns, and `deck.untested` remembers the model. Anything else is refused (`unsupported`, no retrying). A tested model that doesn't report limits falls back to the known ones, so this can't lock out a 1250. **A start never waits:** `Belt.start` drops it when no board is held, and `drop`/`suspend` clear the queue, or the belt would start by itself whenever the board came back.
- **Calories** are active calories (what Apple Fitness counts): ACSM walking/running oxygen cost for speed and grade, less resting 3.5 ml/kg/min, × weight (Settings → You, `deck.weightLb`, default 176 lb), 5 kcal/L. Settings → You also has a distance calibration (`deck.distCal`, ±10%).
- **Workouts:** quick starts in `QUICK` (Walk, Jog, Run, Incline Workout at 3.8 mph and 10%; `inc` and `name` optional), programs in `PROGRAMS`. Intervals is adjustable (1.10.1: Home's workout card → Adjust, `ivSheet`): `IV` in localStorage `deck.intervals` (reps, run and recover speed and length, incline, warm-up and cool-down minutes), rebuilt into `PROGRAMS.intervals` by `buildIntervals`. A free run shows time and miles side by side; slot 1 shows feet climbed. Big Pause and End workout on the run screen.
- **Goals** (1.11.0): Home's quick start card → Goal (`goalSheet`): none, a time (5–180 min) or a distance (0.5–26.25 mi), and a cool-down (0–10 min, default 3), in `GOAL` / localStorage `deck.goal`. `begin()` puts it on the run as `S.goal` for quick starts only (programs end on their own); the run screen shows `#goalLine` under time and miles; `reachGoal()` sets `S.goalHit` and, with a cool-down, `S.cool` (speed down to `COOL_MPH` 3.0 at most, incline 0, `#coolCard` in place of the headline, Keep going restores the speed and incline and carries on), then `finish(false)`. Done's eyebrow says Goal reached; the run record keeps `goal: {kind, value, reached}`.
- **History** (1.9.0): `recordRun` saves every run ≥ 60 s to localStorage `deck.history` (newest first, 1000 max, traces kept for the newest 60); `BESTS` and a "New best" eyebrow on Done; `openHistory` (week from Monday, streak) and `openRun` (a past run in the Done overlay, `S.viewing`). The web demo doesn't record unless `?record`; `?history=sample` seeds sample runs.
- **The mark** (1.10.14): the lap track drawn as a D, lit up the back and over the top, the runner at the front of the curve, on the aqua-to-blue tile. One drawing on a 48 grid, set 15% larger about the tile's centre (1.10.15), in three places: `site/favicon.svg` (and `apple-touch-icon.png`, full-bleed), the site's nav, and `android/res/drawable/ic_launcher.xml`.
- **The site** (`worker/index.js`, Cloudflare Workers + KV): `/` the project page (`site/index.html`), `/console/` the web console (generated), `/app/` the public update channel (manifest and APKs from KV `pub:*`, nothing else reachable), and three private parts behind the deck key (Worker secret `DECK_KEY`, header `X-Deck-Key` or `?k=`): `/update/` (the old channel, from KV `upd:*`; the APKs there before the public build hold the key, so `UPDATE_OPEN` must stay 0), `/diag/` (Diagnostics and motor reports, KV `r:*`, 30 days; `latest`, `latest-<kind>`, `/diag/<id>`), `/runs` (each finished run, KV `run:*`, kept: `/runs/pending` shaped for an iPhone Shortcut that logs runs to Apple Fitness, `/runs/<id>/logged`, `/runs`, `DELETE /runs/<id>`). The app gets the site's address from `Secrets` (generated by build.sh). **The APK is public (1.12.0), so it holds no key:** the site's owner types it once into Settings → Treadmill → Diagnostics → Site key (`Reports.setKey` checks it against `/runs/pending`, then keeps it in prefs `personal`). Without it nothing uploads: runs stay on the console, unsent, and go up once there's a key. The project page's bottom bar is Tommy's shared signature bar, `<tommy-signature>` (v1.0.4): `site/signature/` is the same on all his sites, so don't edit it here.
- **Home Assistant** (optional): the page POSTs to HA webhooks at the address in Settings → Home Assistant (no token; HA takes webhooks from the local network; cleartext allowed in the manifest). `c1250-deck-gym` (Gym lights) and `c1250-deck-tv` with `{cmd}` (the TV remote: up/down/left/right/select/menu/home/play_pause/skip_*, volume_up/volume_down/mute, power, netflix/prime_video/spotify). The automations live in HA; see the owner's notes. Page: `HOOKS`, `haUrl(hook)`, `tvSend(cmd)`, `tvSheet`; native `homeCall(url, body, kind)`.
- **Cameras** (1.10.0): Settings → Cameras signs in with Home Assistant's own login in a dialog over the console (`HomeAuth.java`: client_id `<ha>/`, redirect `<ha>/?deck_auth=1` caught in the WebView, code traded at `/auth/token`; the refresh token stays in the app's private prefs `home_assistant`; bridge `haSignIn/haSignedIn/haBase/haToken/haSignOut`). The page keeps one websocket to HA while signed in (`HA`, `haSend`, `haSub`): `get_states` for `camera.*` (pictures from each one's `entity_picture`, refreshed every 15 s while the sheet is open), live view over WebRTC (`camera/webrtc/get_client_config`, `camera/webrtc/offer` subscription, `camera/webrtc/candidate`; as HA's frontend does it; checked against Ring through HA on 23 Oct 2026), and `subscribe_trigger` on Ring's `event.*` entities whose event_types include `ring`, which opens `camera.<name>_live_view` live (`onDing`; closes itself after 2 minutes). `camSheet` (Choose hides cameras: `deck.camHidden`, entity ids), `camLive`; buttons on Home, the run screen and Paused. Live view sends a `camera` report (`liveReport`, native `sendReport`) when it plays or stalls. On this console Ring's 1920×1080 cameras play (H.264 on the MediaTek decoder, ~1 s), but the doorbell's 1536×1536 never decodes (past the 1080p decoder), so since 1.10.9 video that arrives without decoding falls back to the camera's still picture every 2 s (`startStills`); an offer without H.264 (seen once after a wake) is rebuilt up to 3 times. Picture links carry a token HA rotates every few minutes, so (1.10.11) `refreshCams` reads the states again when the sheet opens and whenever a picture is refused; `loadShot` loads each picture off to the side and swaps it in, and the first sheet of a session sends a `camera` report of which previews loaded. The tiles are `div role=button`, not `<button>` (1.10.17): this WebView shrinks a button's inside to its content, so every preview loaded but was drawn 0 px wide. Sign-in (1.10.4) drops a default port from the base and catches the redirect by its `deck_auth=1` query, since WebView reports `http://host/` for `http://host:80/`. Nothing touches the belt.
- **Start on power-up** opens Android's Home picker (C1250 Deck answers HOME); `BootReceiver` relaunches the app at boot, +20 s and +45 s as a fallback. iFit's own app still came up later and took the screen (26 Oct 2026, on waking the treadmill), so since 1.10.7 `KeepFront` (a foreground service) brings the console back every 3 s for 4 minutes after boot and 2 minutes after the screen comes on, unless we left on purpose (`KeepFront.leaving`: Settings, updates) and at most 20 tries a window; it uploads a `startup` report 3 minutes into each boot (Home app, lock-task state, which iFit apps are device owner or may kiosk-lock, and its log). Waking from sleep isn't a boot, and iFit also took the screen a minute into a session (27 Oct), so since 1.10.8, with Usage access granted (Settings → Keep iFit away, `PACKAGE_USAGE_STATS`, bridge `usageAccess/openUsageAccess`), `KeepFront.watch` checks every 2 s and sends any `com.ifit.*` app in front back behind the console, at any time (resting a minute after 15 in a minute); it reports (kind `startup`, at most every 10 minutes) when iFit takes the screen or the windows give up.
- **Crashes** (1.10.10, after one mid-workout on 27 Oct): an uncaught exception leaves `crash.txt` in the app's files, sent as a `crash` report on the next start; `onRenderProcessGone` reports and recreates the activity instead of letting Android close the app; `KeepFront.onStartCommand` calls `startForeground` every time (a second `startForegroundService` without it closes the app after 5 s). A run in progress is saved every 15 s to `deck.inflight` (`runRecord`, id `S.runId` from its first start) and `recoverInflight` puts it in History, marked `interrupted`, and syncs it on the next start.
- **Sleep** (1.10.18): the app keeps the display powered (`FLAG_KEEP_SCREEN_ON`; Android's own screen-off might not wake on a tap on this console, untested), so sleep is the page's: after `deck.sleepMin` minutes (Settings → Sleep: Never, 5, 10 default, 20, 30) with the belt not running, no countdown, no live camera and no install under way, and no touch (a paused workout waits at least 20 minutes, `PAUSED_MIN`), a minute of dim with a countdown card (1.13.2), then black (`#sleep`, above everything so the tap that snoozes or wakes it never lands on a control). A tap on the countdown, on Snooze or anywhere else, puts sleep off for 20 minutes however short the setting (`SLEEP.floor`). A workout starting, pausing or ending, including from the console's own keys, counts as someone there and restarts the timer. A live camera or an update under way holds sleep off for at most 30 minutes after the last touch (`HOLD_MAX_MIN`, 1.13.3), because a view left open never closed and a page stuck on `confirm` lasted until the next 6-hourly check; going black stops a live view. **Diagnostics → Sleep log** shows the page's setting, what's holding sleep off, and what happened and why, plus `ScreenSleep`'s and `KeepFront`'s logs; it's on screen for a photo, and sent as a `sleep` report if the site key is in. Going black also turns the backlight off (`NATIVE.setSleep` → `MainActivity.setBacklightOff`, `BRIGHTNESS_OVERRIDE_OFF`). A tap, the console's Start key (`startRequested`, which then starts as usual), the doorbell (`onDing`) or coming back to the activity (`onResume`, only with the screen on; `__deckWake`) wakes it. The board has a sleep mode (12) that iFit may use; not written yet. **The backlight override only reaches the panel's minimum on this console; the black still glowed (2 Nov 2026)**, so since 1.11.1 `ScreenSleep.java` can switch the screen fully off: while asleep it drops `FLAG_KEEP_SCREEN_ON` and, with "Modify system settings" granted (`WRITE_SETTINGS`, Settings → Screen off → Allow), sets Android's screen timeout to 10 s, restoring the person's value on waking (and at start, if the app went down asleep). It's only used once Settings → Screen off → Try it has seen something wake the screen (a tap, or the console's Start key: the board stays claimed while our own sleep has the screen off, and Start acquires an `ACQUIRE_CAUSES_WAKEUP` wake lock); Try it wakes the screen itself after 15 s if nothing did, records the result in prefs `sleep`, and sends a `sleep` report. A page wake (doorbell, `setSleep(false)`) also turns the screen back on. **Tested on the console 3 Nov 2026: a tap wakes it from a full screen-off** (Try it result `tap`, woke 2.7 s after the screen went off). The console's own screen timeout was "never" (2147483647 ms), so the permission is needed. **Until 1.13.1 a real sleep didn't hold** (seen 5 Nov 2026): with the screen off the activity stops, `KeepFront` (which also opened a window on SCREEN_OFF) could bring it forward within 3 s, and onStart woke the page and so the screen, which then asked to sleep again 10 minutes later. Reproduced on the emulator with `am start` (`KeepFront`'s flags), since Android 14 may block `KeepFront`'s own start and Android 9 doesn't; not yet confirmed on the console. Now `KeepFront` does nothing while the screen is off, `onResume` only wakes with the screen on, and a SCREEN_ON still true a second later wakes the page (a tap the moment the screen went off never pauses the activity; the delay is because the 3 Nov report shows "on" 24 ms before "off"). Try it's `timer` result now turns full screen-off off. The 3 Nov test ran with `KeepFront` active, so run Try it again on the console rather than relying on it.
- **Updates** (1.10.16): Android 9 always wants a tap on its own Update prompt. An install whose prompt was dismissed or covered without a result left `Updater.busy` set, and since KeepFront keeps the process alive, every later check returned silently and the sheet sat on "Checking for updates…" (28 Oct). Now a check always answers, an install over two minutes old counts as abandoned (`stillBusy`), Install while the prompt is pending shows it again ("Show the prompt again"), and the page gives up on an unanswered check after 30 s.

## Building here
- Android SDK isn't preinstalled. Install command-line tools, then `sdkmanager "platforms;android-33" "build-tools;35.0.0"`, and run `ANDROID_HOME=<sdk> bash android/build.sh`. With `../treadmill-deck-private` present it signs with the real key; without it, it makes a throwaway key. No build holds the site key. `DECK_DEBUG=1` makes a debuggable build with the page open to Chrome's inspector; `release.sh` never does.
- To test the running app, use the Android emulator: `DECK_DEBUG=1 DECK_SITE=http://localhost:<port>` with a throwaway `DECK_PRIVATE` folder, `wrangler dev --var DECK_KEY:<test key> --persist-to <empty folder>` for the site, `adb reverse tcp:<port> tcp:<port>` (`10.0.2.2` didn't reach the Mac), then drive the page over `adb forward` to `webview_devtools_remote_<pid>`. It's Android 14 with no motor board, and a debug-type system image, so it keeps the inspector open even for a non-debuggable app. An attached inspector holds the screen on, so to test sleep, connect only for a moment at a time.
- Use build-tools 35's R8 (build-tools 34's d8 crashes on some inner classes). The JavaScript bridge class must stay a `static` nested class.
- Test the UI in Playwright with a mocked `window.DeckNative` (see the bridge methods in `MainActivity.Bridge`); push state with `window.__deckNative({...})` and `window.__deckHr({...})`. Without the bridge, `?demo=run|workout|paused|done` seeds a screen.
- Before UI work read the Cabin skill (`../cabin/skills/cabin/SKILL.md`: rules, components, tokens).
- The UI is Cabin's Lit finish (Cabin 0.23.0 as of 1.8.0; the version is in the `/* Cabin x.y.z */` line after `cabin:start`): tokens and `cb-*` classes are inlined between `/* cabin:start */` and `/* cabin:end */`; re-run `node ../cabin/scripts/inline.mjs c1250-deck.html --with-components` after a Cabin release. Keep page CSS to what Chrome 80 handles: no `inset`, `aspect-ratio`, `color-mix`, `:has`, and no blur while running. Check with `node ../cabin/skills/cabin/scripts/cabin-lint.mjs c1250-deck.html` (zero errors before shipping; no typed-in colours; third-party brand colours are `--paint-*`).
- Done shows the run over time: the loop samples speed, incline and heart rate every 5 s into `S.trace` and adds seconds per zone to `S.zoneT`; `paintDone` draws a Cabin chart and `cb-zones` for runs of 2 minutes or more. `?demo=done` seeds a full Intervals run.
- The console's WebView has **no flex gap** (Chrome < 84): the page measures it and adds `no-flexgap` to `<html>`, and `.no-flexgap` rules space icons, badges, steppers and button rows with margins. Anything new that relies on flex `gap` needs a rule there (grid gap is fine).
- `[hidden]{display:none !important}` must stay: the overlays set `display:flex`, which otherwise beats `hidden`.
- Don't name a class `app`: it's the page's root container.
- Home sits on a photo: `bg/` holds four cool-graded Unsplash photos and pre-blurred twins (credits in `bg/CREDITS.md`); cards are frosted by lining the blurred twin up behind them (`placeFrost`), never with `backdrop-filter`.

## Publishing an update
1. `bash android/release.sh <version> "<notes>"`: bumps the version, builds and signs, stops if the APK holds the site key or the account id, writes the APK and `manifest.json` to the private repo's `releases/`, and puts both in KV (`pub:*` and `upd:*`) with wrangler (its own login, or `CLOUDFLARE_API_TOKEN` if set; the account id is in `secrets.env`).
   If it says publishing failed, the version is already bumped and the files are in `releases/`: publish those same files (APK before manifest, `pub:` and `upd:`) rather than running it again, which would bump the version again.
2. Commit the version bump here and `releases/` in the private repo; push both.
3. Site or Worker changes: `npx wrangler@4 deploy` (runs `tools/make-site.mjs`).
4. The app reads `<site>/app/manifest.json` (`Updater.DEFAULT_MANIFEST`), with no key. It must stay reachable: moving it needs a release from the old URL first. Consoles older than the public build read `/update/manifest.json` with the key, which is why `release.sh` still publishes to `upd:*`; that stops once none are left.

## Safety
- Nothing starts the belt without `canMove`; keep it that way for anything new that can.
- Install from the app is disabled while the belt is running or paused.
- The console's physical STOP and safety key always override the app.
